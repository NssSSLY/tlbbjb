## 源码发现及影响

1. **旧通用宿主存在必要能力占位。** `original_generic_host.lua:24-33` 中任务刷新/复活为空，可接任务固定 false，转场时间固定返回值。影响依赖这些值的接任务、恢复和等待分支。应逐项实现；未知应有明确结果，不能伪装有效数据。
2. **配置读法不能完整还原原控件。** 同文件 `GetConfigCommbox` 固定空 text，列表项固定 data=0、sel=0。原任务读取文本或附加值时会得到错误语义。应为所改任务声明字段类型、枚举值及列表列结构，再统一转换。
3. **峨嵋待确认动作阻塞后续恢复。** `battle_support.lua:229-249` 先处理 pending，未反馈时最多等待八秒，确认后追加 1500 ms。紧急自保仅能绕过后一个间隔，不能越过 pending。应区分已提交、读条中、动作结束、效果反馈；先读取施法状态，明确允许下一动作时才重新决策，避免既漏救也重复施法。
4. **只治疗同时跳过自身增益。** `battle_support.lua:270` 的输出开关早于 buff 分支。应将恢复、防御增益、进攻增益和攻击分开；只治疗允许已配置且实际支持的防御增益。
5. **治疗缺少距离/视线处置策略。** `emei_support.lua` 有同场景和目标身份校验，但没有独立的治疗范围、视线及失败原因处理。需增加可读取的范围/施法限制，处理不可达队友，避免持续选中同一低血但不可治疗的目标。接口无法取得时显式标注未知，不猜距离。
6. **跨城路由资料未投入执行。** `scripts/navigation/catalog.json` 的 runtime_enabled=false；现有移动主要依赖游戏自动寻路。需统一执行城内移动、跨城 NPC 对话、换图确认、再次导航；按具体副本所需路线逐条补齐。
7. **定时防重复仅覆盖当前运行。** `flow_runner.cpp:40` 每次 start 清空 claimed_；触发时即记录本轮领取日期。重启流程同一窗口可再次发起，失败也不在本轮自动重试。应按角色、节点、活动窗口持久化运行记录，并区分已派发、结果待核验、已完成和可重试失败。重启先核验游戏状态。
8. **新版战斗策略尚未覆盖所有旧入口。** 新三环/老三环、通用战斗和已改技能宿主共用策略，旧原脚本可沿不同调用链执行。逐个迁移时必须列出其实际攻击、恢复、队伍接口，确保配置作用于实际入口。
9. **历史进度文档互相覆盖。** PROGRESS 中旧“当前结论”和后续代码存在时间差；应由任务清单、接口依赖和验证报告生成简短现状表，历史说明只作追溯。

## 推荐实现结构

维持五层：启动器/面板 → 调度器 → 副本规则 → 公共游戏接口 → 驻留引擎。原 Lua 和明文重构规则都调用同一公共接口。

- 公共状态：角色、队伍、目标、技能、任务、NPC 对话、地图；带采样时间和有效性。
- 公共动作：移动、对话、选择、施法、交付；返回已提交、等待反馈、确认、可恢复失败、终止。
- 战斗调度：先处理有效性和紧急自保，再治疗、宠物维护、防御增益和输出。读条期间按游戏实际规则决定是否等待或取消。
- 副本定义：准备、前往入口、接取、集合、入场、战斗阶段、转场、交付、离场、结果；每阶段记录前置条件、动作及推进依据。
- 完成与恢复：每阶段保存最小必要进度，恢复时优先重读游戏状态；只在动作尚未发生或明确可重试时重发。

## 施工顺序与验收

1. 公共战斗收尾：治疗反馈调度、只治疗下的增益、目标不可达处理、下坐骑及 Buff 索引；完成接口级离线场景。
2. 老三环完整收尾：逐段核对八阶段目标、拾取或特殊交互需求、队长/队员、离场和交付；阶段缺口都放在同一副本完成后再开下一项。
3. 新三环：补当前版本何悦多级菜单、三名首领对应阶段、路线和离场，将必须由用户猜填的参数收回为已核验默认规则。
4. 师门：复用上述任务、NPC、移动、战斗接口，按实际任务类型建立分支，不再使用固定 false 的可接任务判定。
5. 其它副本：逐个迁移，每项同时核对配置、依赖、各阶段与结果。

持久化调度与结构化日志可作为公共基础同步修复。日志记录任务/阶段、动作、关键状态变化和退出原因；同状态不刷屏，失败保留有界诊断快照。

## 性能和交付

VM 已有 16 MiB Lua 堆限额、指令及调用时间片。它们不等于整个游戏进程内存限额，也无法抢占正在执行的同步游戏原生函数。应统计原生调用时长、队列积压、扫描次数与 Lua 堆峰值；慢调用必须缩小工作量或拆批。

保持现有合并 DLL/RCC，用户配置、日志、外置脚本独立。短期不更换 Qt 或追求单 EXE；优先明确开发版、安装版、引擎与资源哈希，减少旧版本混用。
